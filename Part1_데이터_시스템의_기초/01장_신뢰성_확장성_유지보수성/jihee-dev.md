# 1장 학습 정리

신뢰할 수 있고 확장 가능하며 유지보수하기 쉬운 애플리케이션  
학습일: 2026-11-25

## 1. 책 내용과 이해한 점

### 신뢰성 — 결함이 있어도 올바르게 동작하는 시스템

오류가 발생하면 빠르게 복구하는 것뿐 아니라, 결함이 발생하더라도 시스템이 사용자에게 기대한 기능을 올바르게 제공하도록 설계하는 것이 중요하다.

- **결함(Fault)**: 시스템의 일부 구성 요소가 명세에서 벗어나는 것.
- **장애(Failure)**: 시스템 전체가 사용자에게 필요한 서비스를 제공하지 못하는 것.
- 모든 결함을 제거하는 것은 현실적으로 어렵다. 결함이 전체 장애로 이어지지 않도록 대비해야 한다.
- 결함은 하드웨어, 소프트웨어, 사람의 실수 등 다양한 원인에서 발생할 수 있다.

**알게 된 점:** 신뢰성은 복구 속도만으로 판단할 수 없다. 결함이 발생했을 때에도 올바른 동작을 유지할 수 있는지가 핵심이다.

### 확장성 — 부하를 설명하고 성능 변화를 판단하기

확장성은 서버를 늘린다는 뜻만이 아니라, 부하가 증가했을 때 시스템이 어떻게 대응할 수 있는지를 설명하는 개념이다.

- 먼저 요청 수, 읽기·쓰기 비율, 데이터 규모, 사용자 관계 등 서비스에 중요한 **부하 매개변수**를 파악해야 한다.
- 부하가 늘었을 때 자원을 유지하면 성능이 얼마나 달라지는지, 성능을 유지하려면 자원을 얼마나 늘려야 하는지 살펴본다.
- 적절한 구조는 서비스의 사용 패턴에 따라 달라진다.

**알게 된 점:** 특정 기술이나 구조가 항상 우수한 것은 아니다. 실제 부하와 요구사항을 알아야 적합한 선택을 할 수 있다.

### 성능 지표 — 평균만으로 사용자 경험을 설명할 수 없다

- 평균 응답 시간이 양호해도 일부 요청은 매우 오래 걸릴 수 있다.
- **P99**는 관측한 응답 시간의 99번째 백분위 경계값이다. 대략 99%의 요청이 이 값 이하에 해당하며, 나머지 약 1%는 더 오래 걸린다.
- 따라서 평균과 함께 상위 백분위수를 확인해야 느린 요청을 경험하는 사용자의 상황을 파악할 수 있다.

**알게 된 점:** P99는 느린 요청 1%의 평균이 아니다. 응답 시간 분포에서 특정 위치를 나타내는 경계값이다.

### 유지보수성 — 운영과 변화까지 고려하기

유지보수성은 코드가 읽기 쉬운지뿐 아니라 시스템을 계속 운영하고 변경하기 쉬운지도 포함한다.


| 요소  | 의미                                    |
| --- | ------------------------------------- |
| 운용성 | 운영자가 시스템 상태를 파악하고 원활하게 운영할 수 있도록 한다.  |
| 단순성 | 불필요한 복잡성을 줄여 시스템을 이해하기 쉽게 한다.         |
| 발전성 | 새로운 요구사항이나 환경 변화에 맞춰 시스템을 수정하기 쉽게 한다. |


**알게 된 점:** 개발 당시 구현을 끝내는 것뿐 아니라 이후 운영과 요구사항 변경에 드는 비용도 설계에서 고려해야 한다.

## 2. 함께 살펴본 개념: Fan-out on Write / Read

피드를 만드는 시점을 달리하면 읽기와 쓰기에 드는 비용도 달라진다.


| 방식               | 동작                          | 장점                            | 부담                           |
| ---------------- | --------------------------- | ----------------------------- | ---------------------------- |
| Fan-out on Write | 게시글 작성 시 팔로워들의 피드에 미리 배포한다. | 읽을 때 이미 준비된 피드를 빠르게 가져올 수 있다. | 팔로워가 많은 계정은 작성 시 배포 비용이 커진다. |
| Fan-out on Read  | 피드를 읽을 때 팔로우한 계정의 게시글을 모은다. | 작성 시 팔로워별로 배포할 필요가 줄어든다.      | 읽을 때 게시글을 조회하고 합치는 비용이 발생한다. |


읽기·쓰기 빈도와 팔로워 분포에 따라 적합한 방식이 달라지며, 계정 특성에 따라 두 방식을 조합할 수도 있다.

**알게 된 점:** 같은 피드 기능도 어느 시점에 계산과 배포 비용을 지불할지에 따라 설계가 달라진다.

## 3. 질문을 풀며 더 이해하게 된 내용

### 결함의 종류에 따라 대응도 달라진다

- 하드웨어 결함에는 디스크 고장처럼 개별 장치에서 발생하는 문제가 있다. 중복 구성으로 대비할 수 있지만, 공통 원인으로 여러 장치가 함께 고장 나는 경우까지 해결되는 것은 아니다.
- 소프트웨어 결함은 같은 코드나 잘못된 가정 때문에 여러 노드에서 동일하게 나타날 수 있다. 같은 프로그램을 실행하는 서버를 늘리는 것만으로 해결되지 않을 수 있다.
- 한 구성 요소의 문제가 다른 구성 요소로 번지는 연쇄 장애를 막으려면 결함의 영향을 격리해야 한다.

**업무와 연결:** 광고 로딩이 실패해도 게시글 본문과 목록은 제공할 수 있도록 설계하는 것이 결함 격리의 예다. 어떤 기능을 반드시 보장하고 어떤 기능은 제한할 수 있는지 요구사항을 먼저 정해야 한다.

### 인적 오류도 시스템 설계의 대상이다

사람에게 주의를 당부하는 것만으로 실수를 없앨 수는 없다. 실수하기 어려운 인터페이스, 반복 작업의 자동화, 변경 전 검증, 모니터링, 되돌리기 쉬운 절차로 오류 가능성과 피해를 줄여야 한다.

**알게 된 점:** 실수를 개인의 책임으로만 보면 같은 문제가 반복될 수 있다. 실수를 예방하고 발견하고 복구하는 구조까지 신뢰성에 포함된다.

### 예측 가능한 부하는 미리 대비할 수 있다

부하가 늘어난 뒤 대응하는 것만이 확장의 방법은 아니다. 특정 시점에 요청이 집중될 것을 안다면 미리 용량을 확보할 수 있다. 이때도 어떤 요청이 얼마나 증가할지, 어느 자원이 병목이 되는지 파악해야 한다.

**알게 된 점:** 확장성을 자동 확장 기능의 유무로만 판단할 수 없다. 부하의 예측 가능성과 운영 방식을 함께 고려해야 한다.

### 처리량·응답 시간·지연 시간은 구분해서 본다


| 개념    | 이번 학습에서 구분한 의미                                            |
| ----- | --------------------------------------------------------- |
| 처리량   | 단위 시간에 처리하는 요청이나 작업의 양.                                   |
| 응답 시간 | 클라이언트가 요청을 보내고 응답을 받을 때까지 걸리는 전체 시간. 네트워크와 대기 시간 등도 포함한다. |
| 지연 시간 | 책의 구분에서는 요청이 처리되기를 기다리는 시간. 실제 처리 시간과 구분한다.               |


처리량이 높다고 각 요청의 응답 시간이 짧다는 뜻은 아니다. 같은 종류의 요청도 실행 시점과 대기 상황에 따라 응답 시간이 달라지므로, 하나의 숫자뿐 아니라 **분포**로 살펴봐야 한다.

### 백분위수는 이상값 자체를 뜻하지 않는다

- **P50**은 중앙값이고, P95와 P99는 각각 응답 시간 분포의 95번째와 99번째 백분위 경계값이다.
- 예를 들어 P99가 800ms라면 관측한 요청의 약 99%가 800ms 이내에 응답했다는 의미다.
- P99를 최댓값이나 이상값 자체로 이해하면 안 된다. 느린 요청들이 있는 분포의 꼬리 부분을 살피기 위한 지표다.
- 요청 비율과 사용자 비율도 다르다. 느린 요청이 약 1%라고 해서 정확히 사용자 1%만 영향을 받는다는 뜻은 아니다.

**알게 된 점:** 평균은 전체적인 수준을, 백분위수는 분포의 특정 위치를 보여준다. 평균이 같아도 일부 요청이 유난히 느린 정도는 다를 수 있다.

### 추상화는 우발적 복잡성을 줄일 때 도움이 된다

문제 자체가 가진 어려움과 구현 방식 때문에 생긴 복잡성은 구분해야 한다. 좋은 추상화는 세부 구현을 감추고 명확한 개념을 제공해 불필요한 복잡성을 줄인다.

반대로 실제 필요보다 많은 계층이나 범용 구조를 만들면 코드를 따라가기 어려워지고 수정 비용이 커질 수 있다.

**알게 된 점:** 추상화가 많을수록 유지보수성이 좋아지는 것은 아니다. 시스템을 이해하고 변경하기 쉬워졌는지가 판단 기준이다.

## 4. 토론 거리

- 우리 서비스의 신뢰성을 판단할 때, 빠른 복구 외에 어떤 동작을 보장해야 할까?
- 평균 응답 시간은 양호하지만 P99가 나쁘다면 어떤 사용자가 영향을 받을까?
- 우리 서비스의 확장성을 설명하는 데 가장 중요한 부하 매개변수는 무엇일까?
- 운영하기 쉬운 구조와 빠르게 기능을 개발하는 구조가 충돌할 때 무엇을 기준으로 판단할까?

## 5. 오늘의 핵심

> 기술 자체의 우열보다 서비스의 부하, 요구사항, 운영과 변화에 필요한 비용을 기준으로 설계 선택을 판단해야 한다.
